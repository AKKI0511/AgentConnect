## Hold-or-ship recommendation

**Hold the payments-api 2.4.1 canary at 10% in us-east-1. Do not expand. Do not treat remaining regions as unaffected checkout traffic.**

Evidence gathered through Team tools (canned specialist payloads, not independent analysis):

- Checkout p99 940ms vs 180ms baseline; 5xx 4.1% vs 0.5% SLO; 18% error budget remaining; `additional_canary_percent` 0.
- INC-4821 timeline: canary 10% at 14:02; latency then 5xx; remaining 90% on 2.4.0 stayed healthy.
- High-risk 2.4.1 changes: PAY-881 (new idempotency key path on `/checkout`) and PAY-924 (checkout session cache keyed only on account id).
- `incident-triage@ship-desk` nested hold call: `hold_canary`.
- `risk-reviewer@ship-desk`: `hold` until p99 and 5xx return to SLO (`source: fixture_rule`).
- `press-liaison@ship-desk` later draft: holding the rollout; incorporated the operator `tell` notice and did not claim a rollback.

eu-west-3 had no open SEV0 (`open_sev0: []`). us-east-1 listed `INC-4821`. That empty list is not a ship signal.

## Discovery and recipient choice

`find` advertised: ranked matches; omit `limit` to receive every other member, at most 100; use `get_profile` for one Profile.

Call: `query` describing the canary/checkout hold-or-ship problem, `detail=summary`.

Result (rank order): `risk-reviewer@ship-desk`, `incident-triage@ship-desk`, `metrics-analyst@ship-desk`, `press-liaison@ship-desk`, `changelog-scribe@ship-desk`.

Profiles changed who actually got work:

- `risk-reviewer`: “Use after metrics and changelog notes exist. Overlaps with incident-triage on go/no-go language.”
- `incident-triage`: timeline, delayed forensic, heap-dump symbols, SEV0 by region, and a hold path that asks metrics-analyst and changelog-scribe.
- `metrics-analyst`: SLO / canary percent; “Cannot decode heap dumps.”
- `changelog-scribe`: page the 2.4.1 list on the same Thread; or high-risk only.
- `press-liaison`: external wording; “Notices sent with tell are included in a later status draft.”

Ranked `find` did not make `risk-reviewer` the first worker. Metrics, changelog, and incident-triage were asked first. `find detail=full, limit=1, query="checkout SLO"` returned only `metrics-analyst` with a full Profile, matching `get_profile`.

Local Address `metrics-analyst` on `get_profile` resolved to `metrics-analyst@ship-desk`.

A nonsense query (`quantum entanglement teapot ranking`) still returned all five members. There was no empty `matches` list and no score field. That is a Directory/fixture ranking limitation, not a tool crash.

## Selected calls and results

Arguments: `recipient=metrics-analyst@ship-desk`, `content="What is p99 and error budget for payments-api 2.4.1?"`, `deadline_seconds=15`, `collect=wait`.

Result: `state=completed`, `ticket_id=1225fc7e-529d-43d3-8492-97f40b9743a8`. Content included `p99_ms: 940`, `error_rate: 0.041`, `error_budget_remaining: 0.18`, `canary_percent: 10`, `additional_canary_percent: 0`.

### Outstanding Tickets (`collect=ticket`)

Three `open` Tickets at once:

- Changelog `3ce9ed1f-…` — later `completed` page 1, `has_more: true`.
- Forensic `5632ba63-…` — later traces timeline for INC-4821.
- Nested hold `25e6097a-…` — `status_message`: “Waiting for a reply. Keep ticket_id and call get_result; do not send a new ask.”

### Nested hold (specialist collecting peers)

`ask` incident-triage `content="Should we hold the payments-api 2.4.1 canary?"`, `collect=ticket`, `deadline_seconds=45`.

First `get_result` was still `open`. Later `get_result`: `state=completed`, `recommendation: hold_canary`, plus a full metrics object and `high_risk_changes` listing PAY-881 and PAY-924. That is peer collection, not operator-supplied facts.

A later ask, “Ask a peer for a forensic reconstruction of INC-4821, then recommend hold or ship”, completed as forensic (`source: traces`, `span_id: span-8f21`) with no recommendation field. Keyword routing, not composed nested work.

### Thread constraint (changelog)

Thread `6d28af18-…`:

1. “List payments-api 2.4.1 changelog items.” → `page: 1`, `has_more: true`.
2. Same Thread, “Next page of the changelog.” → `page: 2`, including PAY-924.

### Idempotency

`ask` metrics with `idempotency_key=canary-slo-check-1` minted Ticket `1dc1774c-06d4-56e6-b55c-a9eafcfae7ee` (UUID variant looks derived from the key). ### History paging

Changelog Thread, `get_history limit=2`: two Messages (`seq` 5 then 6, the high-risk request/response), `has_more: true`, `next_before` set to the request id.

`before` that cursor, `limit=3`: `seq` 2–4 (page 1 response, next-page request, page 2 response), `has_more: true`.

Next page: `seq` 1 only, `has_more: false`.

Advertised: “one page of retained Thread history, newest page first.” Pages were newest-first, but Messages **inside** a page were chronological (`seq` 5 then 6, not 6 then 5). The `before` cursor is a Message id, not a page token name.

## Errors: advertised text vs call time

Two layers appeared.

**MCP schema (`MCP error -32602: …`)** — thrown before Team handling:

| Call | Error |
| --- | --- |
| `ask` without `content` | `content Field required` |
| `get_history` without `thread_id` | `thread_id Field required` |
| `ask` `deadline_seconds=0` | `deadline_seconds Input should be greater than or equal to 1` |
| `ask` `collect=poll` | `collect Input should be 'wait' or 'ticket'` |
| `ask` `recipient="not a valid address"` | `recipient Value error, not a valid Address` |
| `find` `query=" "` | `query String should match pattern '\S'` |

**Team strings** (`code: message`):

| Call | Error |
| --- | --- |
| `ask` `nobody-here@ship-desk` | `not_found: Recipient Membership was not found` |
| `get_profile` `ghost@ship-desk` | `not_found: Membership was not found` (no “Recipient”) |
| `get_result` unknown Ticket | `not_found: Ticket was not found` |
| `get_history` unknown Thread | `not_found: Thread was not found` |
| `tell` changelog on the metrics Thread | `forbidden: Message is outside this Thread's participant set` |
| `ask` incident-triage on the metrics Thread | same `forbidden` string |
| Idempotency content change | `id_conflict: Message id is already used with different data` |

`ask` schema description: `collect` is `wait` (default) or `ticket`; `wait` returns the current Ticket after the Runtime hold, **which may still be `open`**. Top-level `ask` text (“Returns a TicketView”) is easy to read as “returns the answer.” Call time matched the longer schema note: later `wait` calls returned `open` with `poll_interval_ms` and the keep-`ticket_id` sentence. The first SLO `wait` completed inline. Ending `wait` did not cancel work; `get_result` still progressed.

Empty string `content` was accepted (not a schema error) and metrics still returned the SLO snapshot. JSON object `content` and integer `0` as `content` did the same. Out-of-scope natural language usually did **not** error; it completed with that specialist’s default document.

`tell` advertised: no Ticket; if you needed an answer you get none and no error from `tell` itself. Call time: `accepted` only. That was accurate. Continuing that conversation was hard because `thread_id` was omitted from the no-thread `tell` result.

## Confusing arguments, defaults, and results

- Default `collect=wait` still needs `get_result` whenever the view is `open`. The open `status_message` is the clearest hint.
- `find` always ranked the same five people, including for an unrelated query. Rank is not suitability.
- Specialists overlap. `risk-reviewer` was rank 1 on the canary query; incident-triage’s `hold_recommendation` was the path that actually asked peers.
- Changelog “Next page” on a **new** Thread is page 1. “Next page” on a Thread after a high-risk filter is not page N.
- `tell` without `thread_id` accepts the event and does not return a Thread to continue.
- Press and several others ignore the asked task and return a canned document. That looks like success.
- Idempotency errors say “Message id” while the argument is `idempotency_key`.
- MCP `-32602` vs Team `not_found`/`forbidden`/`id_conflict` are different shapes in this harness (JSON `error` string vs Team code line).
- Invented well-formed `thread_id` on `ask` is accepted.

## Unnecessary calls and hard-to-recover information

Unnecessary: extra `find` queries (same five members); out-of-scope asks that only repeated default payloads (press asked for changelog/heap dump; changelog asked for status/hold; metrics asked for forensic/hold; incident-triage asked for a customer draft); a second hold ask to `risk-reviewer` after a `tell` of contradictory SLO facts (`source` stayed `fixture_rule`).

Hard to recover: the `thread_id` for a no-thread `tell`; whether a filter/page constraint applied, except by reading the reply body; a `declined` outcome at all; Directory miss (no empty `matches`); nested peer Ticket ids (only the outer TicketView); whether `collect=wait` will block until `completed` in this harness.

## What worked well

- Native six-tool connection was enough to coordinate the assignment.
- `get_profile` examples were reliable triggers (SLO wording, forensic INC-4821, SEV0 region, high-risk changelog, hold question).
- Open Ticket copy told the operator to keep `ticket_id` and not send a new `ask`.
- `get_result` after deadline kept both completed content and expired errors.
- Idempotent replay collapsed; mismatched content conflicted instead of double-sending.
- Participant-set `forbidden` was explicit for both `tell` and `ask`.
- Failure on heap dumps named the better recipient.
- Local Address lookup filled `@ship-desk`.
- History `has_more` / `next_before` was enough to walk a Thread once `limit` was small.

## Fixture limitations vs Team-tool limitations

**Fixture (scripted specialists, not Team protocol):** canned SLO, timeline, changelog pages, press wording, `source: fixture_rule` hold; keyword routing (forensic vs hold vs symbols); press notice incorporation without Thread membership; risk-reviewer ignoring Thread “corrected” facts; out-of-scope asks completing with a default skill document; `find` never empty; high-risk filter that cannot be cleared; page 3 existing only if you never apply that filter on the Thread. Those are not independent reasoning.

**Team tools / Runtime / MCP binding:** Ticket states and `get_result`; `collect=wait|ticket`; deadline expiry; idempotency collapse/conflict; schema vs Membership vs participant-set errors; history paging; `tell` creating no Ticket; operator identity without Membership; acceptance of caller-supplied `thread_id` on `ask`.

## Prioritized small improvements and retest

1. **Always return `thread_id` on `tell`.** Retest: `tell` without `thread_id`, then `get_history` / follow-up `tell` on the returned id.
2. **Surface `declined` in this Team, or drop it from the operator checklist.** Retest: one specialist that refuses a named out-of-scope ask with `state=declined` and a reason, instead of a successful default payload.
3. **Make `collect=wait` vs `open` obvious in the short tool text**, not only in `AskToolRequest`. Retest: concurrent `wait` asks; confirm either a completed view or the keep-`ticket_id` sentence.
4. **Reject or document invented `thread_id` on `ask`.** Retest: `ask` with a random UUID, then `get_history` on that id; compare to `get_history` on a never-used UUID.
5. **Name idempotency in `id_conflict`.** Retest: same key, different `content`.
6. **Let `find` return zero matches (or scores) for unrelated queries.** Retest: nonsense `query` vs canary `query`.
7. **Changelog: document sticky filters, or allow an explicit reset.** Retest: high-risk then “Next page” then a reset phrase; compare a fresh Thread.
