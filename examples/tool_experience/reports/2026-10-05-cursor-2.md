Tool description excerpts (loaded catalog, not assumed copy):

- **find:** "Find teammates by describing the work you need. Returns ranked candidate cards (address, summary, skill names, tags), not a guarantee of suitability. Call get_profiles when cards overlap. Reuse what you already read. You may conclude nobody fits. Omit limit to receive every other member, at most 100."
- **get_profiles:** "Return selected teammates' Profiles by Address. Pass one or more addresses, at most 20. Duplicate addresses are read once. Missing members appear as per-item errors; other Profiles still return. Prefer this when find cards overlap."
- **ask:** "Send work that needs a reply. Returns the saved request result. If state is open, keep ticket_id and call get_result; do not send another ask to collect. collect=wait bounds this call only and may still return open. deadline_seconds cuts off work, not the wait. Omit thread_id to start a conversation. Continue a returned thread_id only with the same recipient. Prefer this over tell when you need an answer, including acknowledgement that a notice was processed."
- **get_result:** "Return the current saved request result. Repeatable. Does not consume the result. Pass ticket_id from ask. Branch on state. Open means keep waiting with this ticket_id. A completed Ticket stays completed after its original deadline while retained."
- **get_history:** "Return one page of retained conversation history. The newest page is first; turns inside a page are oldest-to-newest. Response and error turns include parent_id, the request Message id they answer (same as that ask's ticket_id). When has_more is true, pass next_before as before. Stop when has_more is false."
- **tell:** "Send work that does not need a reply. Returns a notice acknowledgement. status accepted means the Runtime queued the event, not that the recipient finished processing."

### Catalog mismatches and contract checks

- The catalog included **`get_profiles`** (plural). There was no `get_profile`. I did not call `get_profile`.
- **find** `inputSchema.properties` are only `query` and `limit`. There is **no `detail` argument**. `additionalProperties` is false.
- **get_profiles** takes **`addresses`** (array, 1–20). There is **no DID** field.
- **tell** arguments are `recipient`, `content`, optional `thread_id`, optional `idempotency_key`. There is **no Message envelope** (no `id`, `kind`, `sender`). The live return was `{"status":"accepted"}` (21 characters).
- Descriptions are mostly ordinary language. Type names still leak: `ask` and its `inputSchema.description` say the return is a **TicketView**; `get_result`'s schema description says "Collect the current TicketView". I did not see `TellView` or `HistoryView` in the short tool descriptions. Schema `title` values were request types (`AskToolRequest`, `FindRequest`, `GetHistoryRequest`, `GetProfilesRequest`, `GetResultRequest`, `TellToolRequest`).
- **No `outputSchema`** on any tool in the agent-facing catalog. Each tool had `inputSchema` only.
- **Completed** saved results had `ticket_id`, `thread_id`, `state`, `content` only. **No `ttl_ms`, `deadline`, or `status_message`.**
- **Open** saved results added `deadline`, `poll_interval_ms`, and `status_message`. That is the pending-wait shape, not a terminal failure.
- **Declined** results used `status_message` and no `content`. **Failed** and **expired** used `error.code` / `error.message`. None of those terminal-error shapes included `ttl_ms`.

## Phase 2 confusing arguments, defaults, results, or errors

- Default **`collect=wait` still returned open** for heap-dump symbols and (with `collect=ticket`) for forensic. The catalog warned; Cursor did not auto-poll. I had to keep `ticket_id` and call `get_result`.
- Open views include `deadline` ~1 hour even when the specialist only delays a few seconds. Easy to read as an ETA.
- Press **declined** a request to acknowledge that a tell was processed. The working path is include the fact in a later `ask`.
- Yesterday timeline is **completed + unsupported**, not `declined`. Branch on `content.constraint`, not only `state`.

- Idempotency conflict is readable. Bad-recipient and forbidden errors are short plaintext, not Ticket JSON.

## What worked well (Phase 2 additions)

- `collect=ticket` plus `get_result` on the same id is a usable pending loop.
- History `parent_id` pairs out-of-order and generic replies, including across `next_before` pages.
- Bulk `get_profiles` per-item errors leave other Profiles intact.
- Specialist-to-peer hold recommendation returned metrics and high-risk changelog together.
- Explicit changelog reset then next page continued the unfiltered list on that Thread.
- Prepare/negate press copy refused to claim rollback; confirm did.

## Fixture limitations vs Team-tool limitations

**Fixture:** canned SLO numbers, INC-4821, scripted changelog pages, `source: fixture_rule` on the Phase 1 risk call, specialists that decline or fail specific off-skill asks, forensic delay of a few seconds, press `notices_incorporated` list.

**Team tools:** compact find cards; `get_profiles` addresses and per-item errors; Ticket states including open/expired; `tell` accepted ≠ processed; thread participant `forbidden`; idempotency `id_conflict`; history paging cursors; no `outputSchema`; operator Address on history.

## Prioritized small improvements and how to retest

1. **Add `outputSchema`** (or stop saying TicketView without showing the shape). Retest by loading the catalog before the first ask.
2. **Keep type names out of short descriptions, or use them consistently.**
